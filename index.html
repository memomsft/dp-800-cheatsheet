D1 · Diseñar y desarrollar 35–40 %

M1Objetos de base de datos

  • Tipos: el más pequeño que alcance. decimal(p,s) para dinero exacto, datetime2 mejor que datetime, nvarchar solo si necesitas Unicode.
  • Índices: clustered = ordena la tabla (uno por tabla, casi siempre la PK) · nonclustered = estructura aparte (varios) · INCLUDE = columnas extra para "cubrir" la consulta · filtered = solo las filas del WHERE.
  • Columnstore = analítica (agregaciones, compresión). Rowstore = OLTP.
  • In-memory: SCHEMA_AND_DATA (default, persiste) vs SCHEMA_ONLY (se pierde al reiniciar).
  • Temporal: dos columnas datetime2 + PERIOD FOR SYSTEM_TIME; la history table la maneja el motor. Ledger: updatable (permite UPDATE/DELETE y guarda historial) vs append-only (solo INSERT).
  • JSON: tipo json o nvarchar(max) + ISJSON(). Índice: CREATE JSON INDEX o columna calculada con JSON_VALUE + índice normal.
  • Constraints: PK (único, sin NULL) · FK (ON DELETE CASCADE | SET NULL | NO ACTION) · UNIQUE (admite un NULL) · CHECK · DEFAULT.
  • SEQUENCE es un objeto propio (no va atado a una tabla como IDENTITY).
  • Partitioning: partition function (los límites) → scheme (filegroups) → tabla ON scheme(col). RANGE LEFT: el valor límite queda en la partición de la izquierda; RIGHT: en la de la derecha.
CREATE SEQUENCE dbo.OrderSeq START WITH 1 INCREMENT BY 1;
SELECT NEXT VALUE FOR dbo.OrderSeq;

M2Programabilidad

  • View: guarda una consulta (simplifica y limita acceso). WITH CHECK OPTION evita filas que la view luego no vería. Indexed view = materializada: SCHEMABINDING + índice clustered único.
  • Funciones: escalar (1 valor) · inline TVF (un solo SELECT, la más rápida, "view con parámetros") · multi-statement TVF (más lenta, estimaciones pobres). Regla: prefiere inline.
  • Stored procedure: lógica + parámetros (OUTPUT) + transacciones; se llama con EXEC, no dentro de un SELECT. Buenas prácticas: SET NOCOUNT ON, EXECUTE AS.
  • Trigger: AFTER (después del cambio) o INSTEAD OF (en lugar del cambio; típico en views). Usa las tablas virtuales inserted / deleted. Se dispara por sentencia, no por fila → escribe código para varias filas. Existen también DDL y logon triggers.
  • Atajo: ¿parámetro en el FROM? iTVF · ¿modificas datos o necesitas transacción? SP · ¿reusar un valor dentro de un SELECT? función escalar.

M3T-SQL avanzado

  • CTE: WITH x AS (…). Recursiva = miembro ancla + UNION ALL + miembro recursivo; OPTION (MAXRECURSION n) (default 100; 0 = sin límite).
  • Window: función() OVER (PARTITION BY … ORDER BY …): ranking (ROW_NUMBER, RANK, DENSE_RANK), vecinos (LAG, LEAD), acumulados (SUM() OVER).
  • Graph: WHERE MATCH(a-(arista)->b); SHORTEST_PATH para el camino más corto.
  • Correlacionadas: la subconsulta usa columnas de la externa; EXISTS / NOT EXISTS; CROSS APPLY / OUTER APPLY aplican una función o subconsulta fila por fila.
  • Errores: TRY…CATCH · THROW (moderno; THROW; re-lanza el original) vs RAISERROR (antiguo, formato printf) · SET XACT_ABORT ON · XACT_STATE().

M4Herramientas con IA

  • Instrucciones para Copilot: .github/copilot-instructions.md (todo el repo) · .github/instructions/*.instructions.md con applyTo: "**/*.sql" (solo esos archivos) · AGENTS.md (agentes) · .github/prompts/*.prompt.md (plantillas bajo demanda).
  • Chat: modos Ask / Edit / Agent; eliges modelo y herramientas (tools) en el chat. Las herramientas MCP requieren Agent mode.
  • MCP (Model Context Protocol): estándar para que el asistente use herramientas y datos externos. Config en .vscode/mcp.json (clave servers). Hay servidores para SQL Server (extensión MSSQL / SQL MCP Server) y para un Fabric lakehouse.
  • Copilot in Fabric: necesita una capacidad de Fabric de pago (F2+ / P1+) y que el admin habilite el tenant setting.
  • Seguridad: no pegues secretos ni datos sensibles en prompts · el MCP debe usar una cuenta de solo lectura / mínimo privilegio · revisa el SQL generado antes de ejecutarlo · ojo con prompt injection (datos que traen instrucciones escondidas).

  • Always Encrypted: Deterministic (mismo valor → mismo cifrado; permite =, JOIN, GROUP BY; revela patrones) vs Randomized (más seguro; sin comparaciones). Con enclave se permiten LIKE y rangos. Claves: CMK (p. ej. Key Vault) cifra la CEK; el cliente conecta con Column Encryption Setting=Enabled.
  • DDM: default(), email(), random(), partial(); el permiso UNMASK ve el dato real. No es un control fuerte.
  • RLS: función inline + CREATE SECURITY POLICY. FILTER PREDICATE limita lo que se lee; BLOCK PREDICATE impide escribir filas no permitidas.
  • Permisos: GRANT / DENY / REVOKE; DENY gana. Usa roles, mínimo privilegio y permisos a nivel de esquema.
  • Passwordless: Entra ID + Managed Identity; CREATE USER [x] FROM EXTERNAL PROVIDER; connection string Authentication=Active Directory Default / Managed Identity.
  • Auditing: SQL Server Audit (server audit + audit specification) · Azure SQL Auditing hacia Storage, Log Analytics o Event Hubs.
  • Endpoints de modelos: CREATE DATABASE SCOPED CREDENTIAL … WITH IDENTITY = 'Managed Identity' (sin API keys en texto).
  • Endpoints DAB (REST / GraphQL / MCP): autenticación Entra ID, roles y permisos por entidad y acción, host.mode = production, MCP con permisos mínimos.

M6Rendimiento

  • Tier: DTU = paquete simple · vCore = eliges cómputo y almacenamiento por separado. General Purpose = uso general · Business Critical = baja latencia + réplica de lectura · Hyperscale = bases muy grandes (> 4 TB), escala y restore rápidos · Serverless = se auto-pausa (cargas intermitentes).
  • Planes: actual (lo que pasó) vs estimated. Seek bueno · Scan sobre tabla grande malo · Key Lookup → agrega INCLUDE · avisos de conversión implícita / missing index.
  • Query Store: historial de consultas y planes; Regressed Queries; fuerza un plan con sp_query_store_force_plan. QPI es la vista del portal sobre Query Store.
  • DMVs: sys.dm_exec_requests (qué corre / quién bloquea) · dm_exec_query_stats (consumo acumulado) · dm_tran_locks (locks) · dm_os_wait_stats (esperas) · dm_db_missing_index_* (índices sugeridos).
  • Blocking = espera en cadena (cede al terminar el que bloquea). Deadlock = ciclo; el motor mata una víctima (error 1205). Arreglo: transacciones cortas, mismo orden de acceso, buenos índices, RCSI, reintentos.

M7CI/CD con SQL Database Projects

  • Flujo: proyecto SQL (SDK-style, Microsoft.Build.Sql) → dotnet build → .dacpac → sqlpackage Publish (o azure/sql-action) → base de datos.
  • sqlpackage: Publish (aplica) · Script (genera el T-SQL) · DeployReport (resumen) · DriftReport (¿alguien cambió la BD?) · Extract (BD → dacpac).
  • Pruebas: unit con tSQLt (FakeTable, AssertEquals) vs integration con una BD real o contenedor.
  • Datos de referencia: post-deployment script idempotente (MERGE), versionado en Git.
  • Git: ramas + pull request; branch protection (checks obligatorios y revisores) · CODEOWNERS · Environments con required reviewers para producción.
  • Secretos: GitHub secrets o Azure Key Vault; mejor OIDC (azure/login con id-token: write), sin contraseñas.
dotnet build
sqlpackage /Action:Publish /SourceFile:db.dacpac /TargetConnectionString:"..."

M8DAB y servicios de Azure

  • Data API builder = API REST + GraphQL sobre tablas, vistas y stored procedures, sin código. CLI: dab init, dab add, dab start.
  • Por entidad: source (tabla/vista/SP) · permissions (rol + acciones) · relationships (GraphQL) · cache (enabled, ttl-seconds). Paginación: default-page-size / max-page-size.
  • Consultas: REST $filter $orderby $select $first $after · GraphQL filter orderBy first after.
  • Hosting: contenedor (Azure Container Apps / App Service) u otro servicio de Azure. Monitoreo: Application Insights (telemetría de la app) + Log Analytics (logs/métricas de la BD vía diagnostic settings).

M9Modelos y embeddings

  • Embedding = vector numérico que representa el significado. Se guarda en una columna vector(n); n debe coincidir con el modelo y no se mezclan modelos.
  • Elegir modelo: small (barato y rápido) vs large (mejor calidad, más dimensiones) · multilingüe o multimodal solo si el caso lo pide · structured output = el modelo responde con un JSON que cumple un esquema.
  • Qué incrustar: texto con significado (título + descripción + categoría). No IDs, fechas ni números sueltos.
  • Chunking: trozos de tamaño fijo con solapamiento (overlap) para respetar el límite de tokens.
CREATE EXTERNAL MODEL EmbedModel WITH (
  LOCATION = 'https://<recurso>.openai.azure.com/openai/deployments/<deploy>/embeddings?api-version=...',
  API_FORMAT = 'Azure OpenAI', MODEL_TYPE = EMBEDDINGS,
  MODEL = 'text-embedding-3-small', CREDENTIAL = [https://<recurso>.openai.azure.com]);
SELECT AI_GENERATE_EMBEDDINGS(N'hola' USE MODEL EmbedModel);

M10Búsqueda inteligente

Full-textVectorHybrid
CuándoSKU, error, frase exactapor significado / sinónimosno sabes cómo busca el usuario; RAG
T-SQLCONTAINS FREETEXTVECTOR_DISTANCE VECTOR_SEARCHambos + RRF
  • Funciones: VECTOR_DISTANCE('cosine', a, b) (distancia exacta) · VECTOR_SEARCH (búsqueda aproximada con índice) · VECTOR_NORMALIZE (normaliza el vector) · VECTORPROPERTY (dimensiones / tipo base).
  • Métricas: cosine (la habitual para texto) · euclidean · dot (con vectores normalizados).
  • ENN (exacta): recall 100 %, recorre todo → pocos datos o filtros muy selectivos. ANN (aproximada): recall < 100 % pero rápida → necesita CREATE VECTOR INDEX (DiskANN) y millones de vectores.
  • RRF (Reciprocal Rank Fusion): suma 1/(k + rank) de cada lista (full-text + vector), con k ≈ 60; no hace falta normalizar scores.
-- ENN (exacta)
SELECT TOP (5) id FROM dbo.Docs ORDER BY VECTOR_DISTANCE('cosine', embedding, @q);
-- ANN, docs vigentes
SELECT TOP (5) WITH APPROXIMATE t.id, s.distance
FROM VECTOR_SEARCH(TABLE = dbo.Docs AS t, COLUMN = embedding,
                   SIMILAR_TO = @q, METRIC = 'cosine') AS s
ORDER BY s.distance;
-- ANN, como lo enseña Learn: VECTOR_SEARCH(..., TOP_N = 5)

M11RAG con SQL

  • RAG = Retrieve (busca contexto con vector/hybrid) → Augment (lo mete en el prompt) → Generate (el LLM responde).
  • Úsalo cuando los datos son privados o cambian, necesitas citar la fuente y no quieres reentrenar. Fine-tuning = conocimiento estable que debe quedar dentro del modelo.
  • En T-SQL: sp_invoke_external_rest_endpoint con @url, @payload, @credential y @response OUTPUT (método por defecto POST).
  • Contexto: FOR JSON PATH o JSON_OBJECT + JSON_ARRAY. Respuesta: JSON_VALUE sobre $.result.choices[0].message.content.
  • Seguridad: credencial con Managed Identity; no envíes datos de más; respeta RLS al recuperar el contexto.
DECLARE @response nvarchar(max);
EXEC sp_invoke_external_rest_endpoint
     @url = N'https://<recurso>.openai.azure.com/openai/deployments/<d>/chat/completions?api-version=...',
     @credential = [https://<recurso>.openai.azure.com],
     @payload = @json, @response = @response OUTPUT;
SELECT JSON_VALUE(@response, '$.result.choices[0].message.content');

Cifras que sí conviene saber

MAXRECURSION default 100 (0 = sin límite)
THROW: n.º de error ≥ 50000
Isolation por defecto: SQL Server = READ COMMITTED · Azure SQL DB = RCSI
Deadlock: error 1205
vector: máx. 1,998 dims (float32) · 3,996 (float16)
Dims: ada-002 y 3-small = 1,536 · 3-large = 3,072
RRF: 1/(k+rank), k ≈ 60
sp_invoke_external_rest_endpoint: @timeout 30 s (máx. 230) · @retry_count 0–10
DAB: página por defecto 100, máx. 100,000
EDIT_DISTANCE_SIMILARITY 0–100 · JARO_WINKLER_DISTANCE 0–1 (0 = igual)
Learn vs docs actuales: Learn enseña VECTOR_SEARCH(…, TOP_N = k); la doc vigente usa SELECT TOP (N) WITH APPROXIMATE … ORDER BY distance y marca TOP_N como deprecado. Reconoce las dos formas. Además, JARO_WINKLER_DISTANCE es una distancia (0 = idéntico), no una similitud.
